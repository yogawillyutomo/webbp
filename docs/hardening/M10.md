# M10 — Content Architecture & CMS Readiness

## Status

Implementation complete on the M10 branch and pending final verification/merge.

M10 intentionally keeps WEBBP repository-driven. It does **not** adopt Sanity, Directus, or another CMS provider.

## Baseline

M10 starts from the stable WEBBP v1.0.0 baseline:

- base branch: `main`;
- base commit: `3b373963efad12779de476fcd1f4b1cbdfff2dfe`;
- stable tag: `v1.0.0`.

The public visual and interaction behavior of v1 is the regression baseline for this milestone.

## Goal

Separate public content ownership from React presentation so WEBBP can change content source later without rewriting the public frontend.

The milestone exit condition is that UI presentation consumes normalized public content rather than owning source-of-truth product, solution, company, navigation, contact, legal metadata, or public SEO copy.

## Implemented architecture

M10 introduces a repository-backed content layer under `src/content/` with:

- canonical public content data;
- legal metadata data;
- SEO/social-image data;
- explicit validation modules;
- a normalized server-side repository/query boundary.

Home-page public content now follows:

```text
repository content
      ↓
validation
      ↓
server query / repository
      ↓
src/app/page.jsx
      ↓
normalized public props
      ↓
interactive presentation components
```

Client Components do not import the content repository directly. This is a deliberate future-CMS security boundary.

## Content centralized by M10

The canonical repository-backed layer owns:

- site identity and public metadata;
- public social links and brand assets;
- navigation;
- Hero copy and CTA configuration;
- Solution Domains and product relations;
- Product Portfolio records, statuses, tags, proof, and technology labels;
- Product Portfolio section copy;
- About copy and principles;
- Contact copy and email subject;
- Footer copy and legal links;
- Privacy/Terms metadata and effective-date labels;
- generated social-image copy.

Feature-local duplicate product and solution data sources were removed.

## Presentation boundary

Presentation remains responsible for:

- layout;
- styling;
- animation;
- accessibility behavior;
- responsive behavior;
- focus and modal behavior;
- icons and React components;
- filter and interaction state.

Solution content stores serializable `iconKey` values. The mapping from `iconKey` to a React icon remains presentation-owned.

## Product claim guardrails

M10 does not change the public maturity semantics established at v1.

Controlled product maturity values remain:

- `In Development`;
- `Pre-production`;
- `Prototype`.

The validator rejects unapproved status values and unregistered filter tags. Public product/solution references must resolve.

This validation protects content structure; it does not replace evidence review. A structurally valid statement can still be an unsupported public claim and must be rejected by the evidence-before-claims process.

## Validation gate

M10 adds:

```text
npm run validate:content
```

and changes the standard verification chain to:

```text
npm run validate:content
npm run lint
npm run build
```

through `npm run verify`.

The validation layer covers required fields, unique IDs/slugs/codes, publication flags, controlled maturity vocabulary, registered filter tags, valid relations, icon-key contracts, legal metadata, and social-image content.

## CMS readiness

The intended future path is:

```text
CMS API / SDK
      ↓
server-side CMS adapter
      ↓
WEBBP normalized content model
      ↓
existing query contract
      ↓
existing UI
```

M10 therefore creates a migration seam without adding current CMS operational complexity such as editor accounts, CMS secrets, preview authentication, media lifecycle, provider billing, or cache invalidation.

CMS adoption remains conditional on the triggers documented in `docs/architecture/CMS-STRATEGY.md`.

## Explicit non-goals

M10 does not:

- install or select a headless CMS;
- add product detail routes;
- add case studies or news merely to increase site size;
- change product maturity claims;
- add customer, partner, revenue, SLA, adoption, or legal-company claims;
- move operational product concerns into WEBBP;
- turn WEBBP into Bakaran Platform admin or another tenant application.

Do not merge M10 merely because the architecture is structurally preferable. Merge only after the exact-head verification gate passes and the public v1 regression check is clean.
